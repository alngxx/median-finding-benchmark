# Individual reflection: Quickselect (An Loc Nguyen)

**Worst case.** Quickselect takes O(n^2) time if every pivot is bad, for instance, if each round removes only one element. With a random pivot, no input alone causes this. Only a long run of unlucky pivots does, which is very unlikely. In E3 I ran one instance (n = 10^5, k = n/2) with 1000 seeds. The worst run used 9.86 comparisons per element, 1.95 times the mean of 5.05, nowhere near quadratic. The input that hurts is many equal values with a 2-way partition. On all-equal input, my `select_two_way` removes one element per round. At n = 10^4, it made 37,502,499 comparisons, about 0.375 n^2, against 20,000 (2n) for the 3-way version.

**Hardest bug and decision.** Claude Code wrote a comment saying the expected work is n + 3n/4 + ... = 4n. That assumes every pivot is good, and I did not notice. An independent review caught it, and I redid the argument myself: a pivot lands in the middle half of the list with probability 1/2, and then at most 3/4 of the list remains. That gives T(n) <= 2n + T(3n/4), so at most 8n element visits. E3 measured a mean of 5.05 comparisons per element at k = n/2.

My second mistake was in E5. At k = 9n/10, the median cost was 4.35 comparisons per element, against 3.14 at k = n/10. I blamed our counting rule, which charges 1 comparison for an element below the pivot and 2 otherwise. That was wrong: the expected cost of a round is the same for a position and its mirror. We checked this exactly for every list size up to 60, then ran 300 new seeds. The paired difference was 0.190 with a standard error of 0.123. The gap was noise.

**What I would do differently.** I would use more instances for E5. Ten were too few because, at k = 9n/10, the cost per instance ranged from 2.06 to 5.81 comparisons per element. I would also check the symmetry argument before offering an explanation, not after. I would try an in-place partition that builds no new lists. That would test whether list building slows quickselect at large n. The memory layout explanation accounts for only about half of the increase in time per element, and we did not measure the rest. Finally, I would read Thanh Trung's `median_of_medians.py`, which I did not review carefully and trusted on its passing tests.

**What I did not fully understand before.** I used to think a random pivot works because it is the median on average. It does not. A single pivot can be terrible, yet the expected time is linear. You only need the pivot to land in the middle half with probability 1/2, because then the list shrinks by a constant factor often enough. I also learned that cost depends on k: in my 300-seed run, both ends were cheaper than the middle: 3.98 and 4.17 comparisons per element against 5.07.
